# Taste
- Uses `uv` for Python project and dependency management (creates/syncs deps with `uv sync`, runs things via `uv run`). Confidence: 0.8
- Prefers Flask as the Python web framework for small web apps. Confidence: 0.6
- Extends the client-side bias to code analysis tooling: static checks/linting should be a browser JS script running over the rendered code blocks, not a server endpoint. Confidence: 0.6
- Prefers client-side (browser) rendering for presentation concerns — markdown preview and code highlighting should run in JS libraries in the browser (e.g. marked / highlight.js) rather than server-rendered endpoints; the backend should stay thin (storage + JSON API) and server-side render endpoints can be removed. Confidence: 0.75
- Communicates in Chinese and expects Chinese-language explanations, UI copy, and documentation. Confidence: 0.8
- Terminal/console output (startup banners, log and CLI messages printed by the program) must be in English, even though conversation, docs, and web UI copy are Chinese. Confidence: 0.8
- User-facing docs are bilingual: a Chinese `README.md` plus an English mirror `README.en.md`, with language-switch links at the top of both, kept in sync as content changes. Confidence: 0.65
- Gives very short, high-level feature requests (e.g. one sentence) and expects the agent to pick the implementation approach, wire it in, add tests/docs, and verify, rather than asking clarifying questions. Confidence: 0.75
- Wants Markdown rendering to match GitHub's behavior ("what GFM supports"): GitHub-style alert cards, GFM task lists, and GitHub-like visual treatment of these constructs. Confidence: 0.55
- Wants rich content rendered as a direct inline preview (e.g. Mermaid diagram code blocks turned into SVG in the preview), not as a separate view or export step. Confidence: 0.6
- Third-party frontend libraries are vendored into `static/vendor/` with their LICENSE files and recorded in a vendor README table (marked, highlight.js, DOMPurify, KaTeX, Mermaid, Lezer), rather than loaded from CDNs. Confidence: 0.6
- Expects a repo to carry standard open-source GitHub infrastructure as a set, not ad hoc: `.gitignore`, `LICENSE`, `SECURITY.md`, `CODE_OF_CONDUCT.md`, and "necessary" Issue/PR templates (form-style issue templates, PR template, blank issues disabled). Confidence: 0.55
- Prefers the codebase decomposed by business domain instead of a single monolithic module: one focused blueprint per domain (public pages, console, JSON API, attachments), shared domain logic pulled into a `services.py`, and HTTP handlers left thin. Confidence: 0.6
- Wants shared constants and default settings extracted into one dedicated config module (e.g. `config.py` with a `Config` class plus named constants for limits, ID lengths, regexes, option tuples), so routes/models reference them instead of scattering magic numbers and inline literals. Confidence: 0.7
- Every new feature is expected to land as a complete change: implementation, README/user-facing docs, and pytest coverage, then verified in a real browser before being reported as done. Confidence: 0.65
- Wants a hard, measurable test-coverage quality gate for pull requests: total coverage must be at least 85% and must not drop more than 10% relative to the last checkpoint baseline. Confidence: 0.8
- Uses dated git annotated tags in a `known-good-yymmddhh` format (two-digit year/month/day/hour) as "known-good" checkpoints after changes merge to the default branch, optionally annotated with coverage and environment info (Python/uv versions, OS, browser, database); these checkpoints also define the coverage baseline. Confidence: 0.75
- For multi-user apps, prefers a real account system (register/login/logout, hashed passwords, per-account data isolation) over anonymous, cookie/session-generated identities; rejects "no sign-up" convenience designs when private data is involved. Confidence: 0.65
- Quality/process rules should be written explicitly into `CONTRIBUTING.md` (concrete thresholds, the exact pytest/coverage commands to run, and the tagging procedure), not left implicit in CI config or tooling. Confidence: 0.65
- Prefers a square, un-rounded UI control system: buttons and inputs with zero border radius, theme-colour fill reserved for primary buttons only while secondary buttons keep just a plain border, plus focus animations on every button/input and animated page transitions. Confidence: 0.6
